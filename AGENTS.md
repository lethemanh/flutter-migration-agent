# AGENTS.md — Twake Web-to-Flutter Migration Agent (ADR-001)

> **Do not edit this file by hand.** It is generated from `skills/*/SKILL.md` by `python scripts/gen_agents.py` so that **Codex CLI**, **OpenCode**, **Antigravity**, and other `AGENTS.md` consumers receive all migration rules and workflows in one file.

You are the **Twake Web-to-Flutter Migration Agent**. Migrate Twake React web applications into native Flutter applications while preserving their exact feature set and Twake design system.

## Mandatory Pipeline Order

1. **Discover**: Inventory logic/functions/actions from source with `discover-static`; inspect original UI and asserted action states at `390×844` in the running web app with `discover-runtime`. Reconcile both inventories without silently omitting unresolved behavior.
2. **Pre-Migration Report & Plan — MANDATORY STOP**: Run `plan-migration`; present grouped features/actions, original UI evidence, exact Twake library usage, dependency-ordered feature tasks and the Wave 0–6 plan, including unresolved mobile gaps. Wait for user approval before writing Flutter application code.
3. **Generate Design System**: Run `generate-design-system` from lock-matched web dependencies.
4. **Port Per Feature**: Run `check-feature-gate` before each feature, then implement and verify its behavior. Run the development harness at the end of each implementation wave.
5. **Verify Parity**: Compare valid `390×844` light/dark captures and flow results, then run the final harness via `complete-migration`. Development checks using `--skip-parity` cannot certify completion.

The toolkit is Python. Install it with `python -m pip install -e ".[test]"` and use `twake-migrate` or `python -m twake_migrate`. From a source checkout with an inactive virtual environment, use `.venv/bin/twake-migrate` from the toolkit root. Do not run obsolete Node.js entry points.

## Discover a Twake React Web App for Flutter Migration

### App workspace and continuity

Read the app's `migration.json`, `SKILL.md`, and `progress.json` before working. Create a workspace with `init-app --web <web> --mobile <mobile> --out apps/<app>`; launch with `start --config apps/<app>/migration.json`. Paths in config are relative to the config file unless absolute. `sourceAliases` optionally maps verified app import prefixes to source directories; static tsconfig and bundler aliases are read automatically, while dynamic factories require review. `librarySources` maps npm library names to implementation directories for source inspection; `dependencyRoot` selects installed lock-matched design packages. A sibling checkout is reference material, never permission to replace locked tokens.

Keep all discovery, decisions, plans, screenshots, logs, patches, evidence and reports under `apps/<app>/artifacts/`. Keep app-specific instructions in `apps/<app>/SKILL.md`. The Flutter app contains source, tests, platforms, runtime configuration and its generated `packages/twake_flutter_ui` build dependency. Do not create migration report folders inside it.

After each feature or before stopping, persist `checkpoint --config <config> --state <running|needs-user|blocked|stopped> --reason <specific reason> --next-action <exact next step> --feature <id>`. Continue approved work until complete or a concrete blocker requires user input. A single-feature port is a unit of work, not a reason to end the whole approved migration. Do not ask again for existing approval. Report what passed, what remains, why work stops, and how to resume; never claim silent automatic retries or completion interception in an interactive CLI session.

### Two discovery passes with different sources of truth

**Logic and feature scope come from source code. UI appearance and interaction states come from the running original app.** Do both before presenting a final plan for human approval. A screenshot cannot establish that a function was migrated, and a source import cannot establish what a widget actually looks like.

#### Pass 1 — Source behavior inventory

```bash
twake-migrate discover-static --config apps/<app>/migration.json --out apps/<app>/artifacts/<discovery-run>
```

Use a new output directory when refreshing an approved manifest; preserve existing decisions and approvals. This pass emits:

- `feature-manifest.json`: routes, named/inline components, source-linked action flows, service/API candidates, libraries, locales and a `behavior` inventory.
- `source-behavior.json`: every parsed function/callback/method, call edges, argument expressions, branches, event/configuration handlers, permission/disabled conditions and JSX element props, with exact source files and lines. Direct imports, aliases, named barrel re-exports and namespace calls are linked where statically resolvable.
- `discovery-audit.json`: source hashes and unresolved/dynamic references. Function count is not feature count. Every function must belong to a feature or have a reasoned shared-utility/framework-glue/excluded disposition; reconcile unassigned functions using `functionDispositions[functionId] = {disposition, reason}`. Record `featureReconciliation[manifestId] = {status: reconciled, reviewedBy: agent, notes: ...}` after tracing the feature and its dependencies. Record the app-wide `sourceReconciliation` when all source review is complete. Start original UI discovery for reviewed features while the rest of source reconciliation continues.
- `gap-report.json` and `discovery-summary.md`: candidate mobile gaps and inventory summary.
- `screen-inventory.json`: list of screens, route parameters, and mobile routing stack classification (`shell-drawer-or-tab-root`, `detail-or-parameterized-stack`, `modal-or-fullscreen-form`, `auth-callback-or-login`).
- `ui-component-breakdown.json`: web tables, complex sidebars, modals, nested dropdowns, and hover triggers flagged for conversion to native mobile patterns (`table -> card-list`, `modal -> bottom-sheet`, etc.).
- `api-data-contracts.json`: static API/thunk/WebSocket inventory, enriched during `discover-runtime` with sanitized JSON schemas and OpenAPI 3.1 paths categorized into `uiStateQueries` (`GET`) and `userInteractionMutations` (`POST`/`PUT`/`PATCH`/`DELETE`).
- `state-validation-matrix.json`: extracted state management stores/slices (`createSlice`, `configureStore`, `createContext`), client-side validation rules (regexes, validator calls, JSX field constraints), and client/offline persistence requirements (`localStorage`, `sessionStorage`, `indexedDB`, online/offline listeners).
- `runtime-capture-plan.template.json`: route fixture requirements, bounded sitemap `crawl` settings, and an action checklist. Fill selectors and journeys by inspecting the original app; do not guess them from filenames.

Follow each user action through its handler, callbacks/hooks, store/provider, service/DAO, API/WebSocket operations and resulting state. Inspect validation, authorization/read-only restrictions, confirmation, cancellation, loading, empty, failure, retry and success paths where present. Include secondary menus, dialogs, forms and inline components. Do not replace Copy, Move and Delete with one generic row-action flow or count a button as working because it renders.

Inventory is evidence to guide source review, not a proof of exhaustive static understanding. Resolve callback props, spread props, aliases, higher-order wrappers, object methods, dynamic routes, conditional registrations and library internals before sign-off. JSX routes and static object-router arrays are extracted; unresolved factories/spreads/paths remain explicit review items. Inspect configured library implementations and bundler aliases. Record the agent reconciliation in `discovery-audit.json.sourceReconciliation`. After both passes and explicit human scope approval, record `review.status: reviewed`, `reviewedBy` and `notes`; this human review is separate from the agent reconciliation. Changed source files invalidate it.

#### Pass 2 — Observe the original UI and action outcomes

Run the web app itself. At 390×844, inspect the relevant source-derived screens and action states in light and dark mode. Capture the first feature slice early and finish app-wide observation before final verification. Use the app's real theme controls, persisted theme setting or system color scheme. Never force a `data-theme` attribute, inject guessed styles, or assume an unchanged screenshot proves dark mode.

```bash
twake-migrate discover-runtime --url <running-web-url> \
  --manifest <discovery-dir>/feature-manifest.json --gaps <discovery-dir>/gap-report.json \
  --capture-plan <discovery-dir>/runtime-capture-plan.json --out <discovery-dir>
```

Supply authorized browser session/route fixtures when authentication or real entity IDs are needed. Each configured journey selects a manifest route and explicit browser steps (`click`, `fill`, `press`, `selectOption`, `check`, `uncheck`). Link the initiating or resulting callback using `sourceActionId`. Every step must assert a visible/hidden/enabled/disabled/text outcome; `expectResponse` can assert a same-origin endpoint's method and HTTP status without recording tokens or response bodies.

Example structure (replace IDs/selectors with observed app values):

```json
{
  "journeys": [{
    "id": "open-action-dialog",
    "routeId": "ROUTE_EXAMPLE",
    "readOnly": true,
    "steps": [{
      "sourceActionId": "ACTION_FROM_SOURCE_INVENTORY",
      "action": "click", "selector": "[data-testid=observed-action]",
      "expect": [{"selector": "[role=dialog]", "state": "visible"}]
    }]
  }]
}
```

Confirm read-only journeys from source behavior. Opening a dialog and cancelling can usually be inspected without changing data. Do not submit create/update/move/delete operations against real data without explicit authorization; `--allow-mutations` is only for already-authorized journeys. Use disposable fixtures or controlled failure responses for mutation/error branches when authorized.

Capture before/after screenshots, computed styles, layout bounds, compact ARIA accessibility trees (`ui.accessibilityTree`), accessible control labels and disabled/required/read-only states. Observe conditional menus, dialogs, validation/errors and permission variants using appropriate fixtures. Do not infer invisible states from the default screen. Input values, credentials and raw response bodies are not part of DOM metrics; `page.on('response')` records only structural JSON schemas and HTTP status codes into `api-data-contracts.json`, and the sitemap records visited manifest routes and observed local links.

Use the static manifest as the runtime sitemap. Visit each configured route fixture directly. Record links for review without following them. Drop query strings and fragments from sitemap identity and collapse concrete paths into their manifest templates. Preserve approved query values in explicit capture fixtures and journeys.

For optional exploration, add up to three source-verified read-only CSS selectors in a route fixture's `explore` list. These clicks run once per route template after the light baseline. Exploration stops at 30 steps or 60 seconds of probe time. Lower limits through `crawl.maxSteps`, `crawl.timeoutSeconds` and `crawl.maxPages`. Block an element for the rest of exploration when its click changes neither the canonical route nor produces a network response. Keep scripted assertions for modal and other DOM-only states in `journeys`. Their evidence remains separate from exploration. For integrations using the synchronous discovery loop, send the initial prompt and at most the last two steps to each decision, and keep full history on disk.

Discovery permission tiers apply at execution. Run routine discovery commands, launch the Playwright browser, and open configured app links without asking. Use `navigate` or `open_link` for direct visits to manifest route fixtures. Read-only tools run automatically within the configured origin and artifact directory. Interactive clicks and fills require a source-verified selector allowlist supplied by the host as `benign_selectors[routeTemplate][action]`. Runtime probes use each route fixture's `explore` allowlist. During unattended interactions, intercept HTTP requests and allow same-origin read methods only. Use mock inputs for exploratory fills.

Unknown interactive selectors stop the exploration loop for a decision. Delete, cancel-subscription, checkout, submit controls and declared write requests require explicit human authorization even if a selector is listed as benign. Run these as scoped scripted journeys with `--allow-mutations` after authorization. The browser request guard supplements source review. It covers routed HTTP requests during the interaction window.

`runtime-discovery.json` maps screenshots/assertions to source action IDs. A route screenshot alone cannot cover an action. Missing action themes, missing screens, skipped routes, disabled theme verification or failed expectations keep discovery partial or failed. Partial evidence can support scope approval and readiness for individual features. Only explicit user approval authorizes Flutter implementation. Discovery observations describe original behavior and do not certify native parity.

#### Record the app's authentication flow

Trace login, session initialization and logout from this app's source and related libraries. Record the mechanism, sequence, environment/redirect configuration, bootstrap requirements, storage, native lifecycle/recovery behavior and evidence in `apps/<app>/SKILL.md`. Authentication may differ between apps; shared instructions do not prescribe another app's protocol, native library, callback adapter, backend endpoint or platform settings. #### Reconcile before planning

Compare both passes: every source action/function needs a feature disposition, and every observed control/state needs a source explanation. Correct missing manifest entries, merge callbacks into meaningful user-facing features, and preserve existing mobile decisions. List unresolved code, unavailable UI states or required fixtures explicitly. Then run `plan-migration`; if evidence is incomplete, produce a draft with blockers rather than silently excluding behavior.

## Pre-Migration Report & Phased Migration Plan

Logic scope must be established from source, and UI states must be observed in the original running app. Never start migrating Flutter features immediately after a static scan. Immediately after `discover-static` and original-app `discover-runtime` observation, you MUST generate and present the **Pre-Migration Report & Plan** and wait for the user's explicit approval.

### Step 1 — Generate the Pre-Migration Plan (`plan-migration`)

```bash
twake-migrate plan-migration \
  --manifest <discovery-dir>/feature-manifest.json \
  --gaps <discovery-dir>/gap-report.json \
  --widget-map <twake_flutter_ui-dir>/widget-map.json \
  --runtime-report <discovery-dir>/runtime-discovery.json \
  --out <discovery-dir>
```

The runtime report defaults to the manifest directory when `--runtime-report` is omitted. The plan lists readiness per manifest ID. Once at least one feature has current source and original-app evidence, present the scope and outstanding work for explicit approval. With approval, port only features that pass `check-feature-gate`. The final harness still requires complete discovery and native parity. Rerun planning as evidence arrives. A plan generated by this workflow preserves its recorded approval when the manifest scope, gap decisions and source fingerprints match.

This produces:
- `migration-plan.json` — machine-readable plan gated by `approval.status` (`"pending-review"` until approved).
- `feature-review.json` — grouped source-derived feature candidates with actions, functions, source spans, UI evidence and unresolved function dispositions. Do not treat each callback/API call as a separate confirmed user-facing feature.
- `migration-tasks.json` — source reconciliation and original-UI prerequisites, human approval, then per-feature logic/UI/verification tasks. Action implementation and outcome checks are nested subtasks with dependencies and acceptance criteria. Keep related actions with their owning feature; do not create unrelated feature folders for every handler.
- `migration-plan.md` — structured report containing:
  1. **Part 1 — All Discovered Features**: Every route, screen, user flow, reusable component, Redux/WebSocket operation, and `twake-i18n` locale/key count.
  2. **Part 2 — All Twake-Related Libraries**: Every `@linagora/*`, `twake-*`, and `cozy-*` dependency (`@linagora/twake-css`, `@linagora/twake-mui`, `@linagora/twake-icons`, `twake-i18n`, `@linagora/twake-oidc`, `@linagora/twake-utils`, `@linagora/twake-websocket`), the exact symbols/components/icons/utility classes used in the web app, how each maps to Flutter, and which `twake-mui` widgets are not yet mapped in `widget-map.json`.
  3. **Part 3 — Phased Migration Plan (Wave 0 → Wave 6)**: Dependency-ordered steps mapping Manifest IDs and React source files to target Flutter files, marking each step `READY` or `BLOCKED`.
  4. **Part 4 — Mobile View Decisions & Open Questions**: Distinguishing patterns automatically resolved by the web app's own `isMobile` branch from web-only patterns (`unresolved-ask-user`) that require user input.
  5. **Part 5 — Feature Tasks and Review Checklist**: Grouped features and their exact source actions, reached functions/services, original UI references, missing observations, implementation/test subtasks, dependencies, and acceptance criteria for observable outcomes. Unassigned functions and unresolved references remain review work.

   - How to resolve any `unresolved-ask-user` mobile gaps.
3. Only after user confirmation, mark `feature-manifest.json` and `migration-plan.json` as `--approve` and proceed to Wave 0 / Wave 1.


Before requesting plan approval, reconcile the scope inventory and the source and runtime behavior of the first ready features. Keep outstanding evidence visible in the plan. Task completion must be observable: preserve the source trigger/guard, handler and service effects; assert the expected success/error/cancel/retry state; compare original/native UI where relevant. ## Generate and Maintain `twake_flutter_ui`

Flutter cannot import npm packages directly. Instead, `twake_flutter_ui` is deterministically generated from the Twake repositories so the mobile app uses the exact same tokens, icons, utilities, and translation keys.

### Step 1 — Run the Deterministic Generator

```bash
twake-migrate generate-design-system \
  --web <path-to-react-repo> \
  --out <path-to-twake_flutter_ui>
```

### What Is Generated (Never Hand-Edit)

| Source Package | Generated Flutter Artifact | Purpose |
|---|---|---|
| `@linagora/twake-css` (`palette.json`, `vars.scss`) | `lib/src/tokens/twake_palette.dart` | Full color ramps + semantic light/dark tokens |
| `@linagora/twake-mui` (`makeTypography.ts`) | `lib/src/tokens/twake_typography.dart` | `Inter` typography scale (`h1`–`overline`) |
| `@linagora/twake-mui` (`radius.ts`) | `lib/src/tokens/twake_radius.dart` | Border radii (`none`, `sm`, `shapeDefault`, `md`, `lg`, `pill`) |
| `@linagora/twake-css` (`config.scss`, `spaces.scss`) | `lib/src/tokens/twake_spacing.dart` | Named spacing (`xs`–`xxl`), utility steps (`u0`–`u3`), `EdgeInsets` presets (`p1`, `mb1`, etc.) |
| `@linagora/twake-mui` + `twake-css` | `lib/src/theme/twake_theme.dart` | `TwakeTheme.light()` and `TwakeTheme.dark()` |
| `@linagora/twake-icons` (`assets/ui/*.svg`, `assets/illus/*.svg`) | `lib/src/icons/twake_icons.dart` + SVG assets | `TwakeIcons.<Name>` and `TwakeIcon` widget |
| `@linagora/twake-mui` components | `lib/src/components/twake_components.dart` + `widget-map.json` | 1-to-1 widgets (`TwakeLayout`, `TwakeAvatar`, `TwakeSearchBar`, `TwakeEmptyState`, `TwakeSegmentedTabs`) |
| `@linagora/twake-utils` (`twake-ts-utils`) | `lib/src/utils/twake_utils.dart` | `TwakeUtils.resolveUriTemplate`, `buildMailComposerUrl`, `buildCalendarEventUrl`, `resolveChatSpaUrl` |
| `twake-i18n` (`locales/*.json`) | `lib/src/l10n/app_<locale>.arb` + `twake_i18n.dart` | All 7 locales (`de`, `en`, `es`, `fr`, `it`, `ru`, `vi`) + `TwakeI18n.t()` |

### Missing Component Rule

Before porting a feature, check `widget-map.json`. If a `@linagora/twake-mui` component has `status: "unimplemented"`, stop and either ask the user or add the 1-to-1 widget to `twake_flutter_ui` first. Never improvise ad-hoc widget styling inside feature code.


### Preserve Values and Effective Widget Styles

Read the actual source token definitions; importing token names alone does not establish parity. Extract typography variants from `makeTypography.ts` rather than maintaining handwritten values. Preserve font size, weight, line height (convert pixel line heights to Flutter height ratios), letter spacing, and every variant present in the resolved version. Do not add variants from a newer version. Fail explicitly when the source shape is unsupported instead of silently using stale values.

Map semantic roles into the effective Flutter component themes in both light and dark modes. Flutter Material defaults can introduce unrelated surface tints, colors, typography, field borders, button shapes, and dialog radii even when the palette file is correct. Inspect `makePalette.ts`, `makeTheme.ts`, component overrides, and the web screen's mobile classes; do not assume a Flutter AppBar title uses the same variant as the web mobile title. Fix the generator and regenerate; never patch generated files.

Verify resolved styles on rendered widgets as well as source token values. Run light/dark checks and compare 390×844 captures before claiming visual parity. Record remaining component/layout differences separately from token fixes.

### Resolve and Validate the Web Dependency Versions

Use the target web app's lockfile and resolved packages as the design source. Never silently substitute the latest sibling Twake checkout. Check package versions and lockfile integrity against the target web lockfile before generation. Stale `node_modules` must block generation. If necessary, install exact locked packages into an isolated cache and pass `--dependency-root <cache>`; do not upgrade the web app to make extraction convenient. Investigate bundler aliases if they override normal package resolution.

The generator parses installed `dist/lib/*.js` token expressions with a Python tree-sitter AST and reads compiled CSS utility dimensions and the installed icon sprite. Unsupported expressions must fail explicitly. Source paths, versions, hashes and generated-file hashes are recorded in `version-lock.json`. Run `twake-migrate validate-design-tokens --ui <package>` after generation; the harness also checks source-to-Dart typography, semantic colors, spacing and radii and detects stale or modified generated files.

`harness-check` requires decoded-pixel visual parity by default. `--skip-parity` is for development only and must never be reported as completion. Supply real 390×844 light and dark screenshots named `<screen-id-lowercase>-<theme>.png`, together with flow results, to `verify-parity`. Invalid PNGs, missing themes, incorrect dimensions and missing baselines must fail. PNG encoding/compression differences alone must not count as visual differences.

## Port a Feature from React Web to Flutter

**One port unit = one manifest feature.** Continue to the next approved feature after verification; one unit does not end the approved migration. Never invent features, screens, routes, actions, or translation keys that are not in `feature-manifest.json`.

### Step 1 — Pre-Flight Feature Gate

Before writing any Dart code for `<MANIFEST_ID>`, run `check-feature-gate`:

```bash
twake-migrate check-feature-gate \
  --manifest <manifest-path> \
  --gaps <gap-report-path> \
  --widget-map <widget-map-path> \
  --feature <MANIFEST_ID>
```

- If `check-feature-gate` exits with `BLOCKED_UNRESOLVED_MOBILE_GAP`, **stop immediately and ask the user** how the web-only pattern should work on mobile.
- If it exits with `BLOCKED_MISSING_COMPONENT`, **stop** and add the missing component to `twake_flutter_ui` or ask the user.
- If `hasWebMobileAdaptation` is `true`, read the source React file's `isMobile` / `useBreakpoints()` branch and **copy that exact mobile behavior**.

### Step 2 — Write Flutter Code with Mandatory Traceability Headers

Every Dart file under `lib/` MUST begin with:

```dart
// @manifest-id: <ID_1>, <ID_2>
// @source-react: <relative/path/to/ReactFile.tsx>
```

#### Architecture & Token Rules
- **Token enforcement**: Follow the token rules while implementing. The wave-end harness validates app aliases and generated token values.
- **Architecture**: Feature-first folders (`lib/features/<feature>/screens/`, `widgets/`, `providers/`), `flutter_riverpod` for state, `go_router` for routing.
- **Colors**: Use `TwakePalette.*`, `AppColors.*` (`lib/core/theme/app_colors.dart`), or `Theme.of(context).colorScheme`. Never use `Color(0x...)`, `Colors.*`, or raw hex strings (`'#FF5733'`).
- **Typography**: Use `TwakeTypography.*`, `AppTypography.*` (`lib/core/theme/app_typography.dart`), or `Theme.of(context).textTheme`. Never pass `TextStyle(`, `fontSize:`, or `fontWeight:`.
- **Spacing**: Use `TwakeSpacing.*` (`TwakeSpacing.p1`, `TwakeSpacing.mb1`, `TwakeSpacing.m`) or `AppSpacing.*` (`lib/core/theme/app_spacing.dart`). Never pass numeric literals to `EdgeInsets.*` or `SizedBox(height/width: ...)`.
- **Radius**: Use `TwakeRadius.*` or `AppRadii.*` (`lib/core/theme/app_radii.dart`). Never pass numeric literals to `BorderRadius.circular`.
- **Icons**: Use `TwakeIcon(icon: TwakeIcons.<Name>)`. Never use Material `Icons.*`.
- **Strings**: Use `TwakeI18n.t('<key>')` with an existing key from `feature-manifest.json`.
- **Auth**: Follow the selected app skill’s source-traced authentication flow; see App-specific authentication below.

### App-specific authentication

Read the selected app's `apps/<app>/SKILL.md` authentication section before porting login, callbacks, session startup or logout. That app skill owns the source-traced sequence, protocol and native library choice, environment configuration, registered redirects, backend bootstrap, storage, lifecycle and recovery rules, plus verification evidence. Do not apply another app's flow, endpoints, callback adapter or platform settings by default.

During discovery, trace the target source and related authentication libraries, then record the findings in that app skill. If authentication is absent, record the source evidence for that finding. If it is unresolved, record the missing information and resolve it before implementing auth. Preserve credential confidentiality and the applicable protocol's security guarantees; verify the complete app-specific login/session/logout journey, including recovery, against the original behavior. Shared instructions do not select an authentication protocol or implementation.

### Step 3 — Verify Feature Behavior and Close the Wave

Run focused Flutter analysis, tests, and runtime checks for the feature. Record implementation and behavior evidence in the app workspace and continue with the next approved feature in the wave.

After finishing the wave's planned Flutter work, run `check-app --config <config> --development` once for the wave. If it fails, fix the findings and rerun at the same checkpoint. Defer the app-wide harness during individual feature edits and subtasks.

At final verification, run `verify-parity --flutter <app>` with the current original and native screenshots and flow results. Then run `complete-migration`, which runs the final harness and records the verified source revision on success. Final verification requires full coverage, an approved plan, reviewed discovery, current feature evidence and current parity. A development report cannot certify completion.

## Twake Web-to-Flutter Harness Guardrails

The harness enforces 8 mechanical checks (`twake-migrate harness-check`) to check whether the Flutter app preserves the Twake UI system and web feature set without hallucinating or dropping behavior:

1. **Manifest-Gated Generation (`[MISSING_MANIFEST_ID]`, `[MANIFEST_NOT_APPROVED]`)**
   - `feature-manifest.json` must have `approval.status === "approved"`.
   - Every `.dart` file in `lib/` must have a `// @manifest-id: <ID>` header referencing valid IDs from `feature-manifest.json`.
2. **Source Traceability (`[MISSING_SOURCE_TRACEABILITY]`, `[BROKEN_SOURCE_TRACEABILITY]`)**
   - Every `.dart` file in `lib/` must have a `// @source-react: <path>` header pointing to the actual React `.tsx`/`.ts` file in the web repository.
3. **Reverse Check — No Invented Features (`[REVERSE_CHECK_INVENTED_*]`)**
   - Any `GoRoute(path: ...)` not in `manifest.routes` fails the build.
   - Any `@manifest-id` not in `feature-manifest.json` fails the build.
   - Any `TwakeI18n.t('...')` key not in `manifest.i18n.keys` fails the build.
4. **Coverage Check (`[INCOMPLETE_COVERAGE]`)**
   - Final checks require full `routes`, `screens`, `components`, `flows`, and `apiCalls` coverage by default. Development checks with `--skip-parity` may be partial.
   - Headers count traceability only. Use `record-feature --manifest <manifest> --flutter <app> --feature <id> --implementation lib/<file>.dart --verification <test-or-runtime-log> --out <workspace>/artifacts/feature-evidence.json` for each item. Final harness requires `--evidence <file>`, current implementation/verification hashes, and the matching manifest hash. Evidence files must describe behavior tested; their existence alone is not proof of feature correctness.
   - Newly generated plans track discovery readiness per feature. The development harness checks readiness for referenced features. The final harness requires complete, current app-wide discovery. Task dependencies and action outcome checks live in `migration-tasks.json`.
   - Final verification requires a human-reviewed discovery audit and unchanged source fingerprints. Unrecognized/dynamic source patterns require manual reconciliation before approval.
5. **Token Value Validation and Linter (`[TOKEN_LINT_*]`)**
   - Validates generated token values against lock-matched web sources and rejects source/generated-file drift.
   - Run the app-wide checks explicitly at the end of each implementation wave and at final verification. `HarnessOrchestrator` only intercepts completion in integrations that call its API; the launcher does not connect it to Codex. This API checks token syntax, not overall migration completion.
   - App theme/token definition files are scanned too; renaming a file cannot exempt hardcoded widget styles. Generated library tokens are checked separately against web sources.
   - Forbids `Color(0x...)`, `Colors.*`, and raw hex strings -> require `TwakePalette`, `AppColors` (`lib/core/theme/app_colors.dart`), or `ThemeData`.
   - Forbids `TextStyle(`, `fontSize:`, and `fontWeight:` -> require `TwakeTypography`, `AppTypography` (`lib/core/theme/app_typography.dart`), or `Theme.of(context).textTheme`.
   - Forbids numeric `EdgeInsets.*` and `SizedBox(height/width: ...)` -> require `TwakeSpacing` or `AppSpacing` (`lib/core/theme/app_spacing.dart`).
   - Forbids numeric `BorderRadius.circular` -> require `TwakeRadius` or `AppRadii` (`lib/core/theme/app_radii.dart`).
   - Forbids `Icons.*` -> require `TwakeIcons`.
6. **Missing-Component Gate (`[BLOCKED_MISSING_COMPONENT]`)**
   - Fails if a referenced manifest item uses a `@linagora/twake-mui` component marked `unimplemented` in `widget-map.json`.
7. **Mobile-View & Gap Gate (`[BLOCKED_UNRESOLVED_MOBILE_GAP]`)**
   - If the web app has a mobile view (`isMobile` / `useBreakpoints`), copy it.
   - If a component has an entry in `gap-report.json` with `status: "unresolved-ask-user"`, the harness blocks porting until the user resolves it.
8. **Parity Gate (`[PARITY_GATE_FAILED]`)**
   - Required by default: compares decoded pixels in valid 390×844 light/dark screenshots plus interaction flows. `--skip-parity` is explicitly development-only; it cannot certify completion.


Use `check-app --config apps/<app>/migration.json --development` once at the end of each implementation wave. At migration completion, use `complete-migration --config apps/<app>/migration.json`, which runs the final harness itself. Reports are written in the app workspace. A passing development check never certifies completion. Final parity must cover every screen and associated flow; reports are tied to manifest, Flutter source and screenshot/flow input hashes. Generate final parity with `verify-parity --flutter <app>` so Flutter source changes invalidate it. Mechanical checks cannot establish that a handler or screenshot represents the intended behavior; retain source review and real device/runtime validation.
