# Pre-Migration Report & Phased Migration Plan

Logic scope must be established from source, and UI states must be observed in the original running app. Never start migrating Flutter features immediately after a static scan. Immediately after `discover-static` and original-app `discover-runtime` observation, you MUST generate and present the **Pre-Migration Report & Plan** and wait for the user's explicit approval.

## Step 1 — Generate the Pre-Migration Plan (`plan-migration`)

```bash
twake-migrate plan-migration \
  --manifest <discovery-dir>/feature-manifest.json \
  --gaps <discovery-dir>/gap-report.json \
  --widget-map <twake_flutter_ui-dir>/widget-map.json \
  --runtime-report <discovery-dir>/runtime-discovery.json \
  --out <discovery-dir>
```

The runtime report defaults to the manifest directory when `--runtime-report` is omitted. The plan lists readiness per manifest ID. Once at least one feature has current source and original-app evidence, present the scope and outstanding work for explicit approval. With approval, port only features that pass `check-feature-gate`. The final harness still requires complete discovery and native parity. Rerun planning as evidence arrives. A plan generated by this workflow preserves its recorded approval when the manifest scope, gap decisions and source fingerprints match.

This produces:
- `migration-plan.json` — machine-readable plan gated by `approval.status` (`"pending-review"` until approved).
- `feature-review.json` — grouped source-derived feature candidates with actions, functions, source spans, UI evidence and unresolved function dispositions. Do not treat each callback/API call as a separate confirmed user-facing feature.
- `migration-tasks.json` — source reconciliation and original-UI prerequisites, human approval, then per-feature logic/UI/verification tasks. Action implementation and outcome checks are nested subtasks with dependencies and acceptance criteria. Keep related actions with their owning feature; do not create unrelated feature folders for every handler.
- `migration-plan.md` — structured report containing:
  1. **Part 1 — All Discovered Features**: Every route, screen, user flow, reusable component, Redux/WebSocket operation, and `twake-i18n` locale/key count.
  2. **Part 2 — All Twake-Related Libraries**: Every `@linagora/*`, `twake-*`, and `cozy-*` dependency (`@linagora/twake-css`, `@linagora/twake-mui`, `@linagora/twake-icons`, `twake-i18n`, `@linagora/twake-oidc`, `@linagora/twake-utils`, `@linagora/twake-websocket`), the exact symbols/components/icons/utility classes used in the web app, how each maps to Flutter, and which `twake-mui` widgets are not yet mapped in `widget-map.json`.
  3. **Part 3 — Phased Migration Plan (Wave 0 → Wave 6)**: Dependency-ordered steps mapping Manifest IDs and React source files to target Flutter files, marking each step `READY` or `BLOCKED`.
  4. **Part 4 — Mobile View Decisions & Open Questions**: Distinguishing patterns automatically resolved by the web app's own `isMobile` branch from web-only patterns (`unresolved-ask-user`) that require user input.
  5. **Part 5 — Feature Tasks and Review Checklist**: Grouped features and their exact source actions, reached functions/services, original UI references, missing observations, implementation/test subtasks, dependencies, and acceptance criteria for observable outcomes. Unassigned functions and unresolved references remain review work.

## Step 2 — Present to User and Wait for Sign-Off

1. Present the discovered feature/action list, exact library usage, original UI evidence, open gaps, and dependency-ordered feature/task breakdown. Distinguish verified observations from candidates and blockers. Generic titles such as “primary interaction flow” do not replace actual actions.
2. Ask the user to confirm:
   - The phased migration plan and target Flutter architecture.
   - How to resolve any `unresolved-ask-user` mobile gaps.
3. Only after user confirmation, mark `feature-manifest.json` and `migration-plan.json` as `--approve` and proceed to Wave 0 / Wave 1.


Before requesting plan approval, reconcile the scope inventory and the source and runtime behavior of the first ready features. Keep outstanding evidence visible in the plan. Include secondary interactions and library-provided behavior. Preserve existing approval and gap decisions when resuming; new scope or unresolved UX requires a focused review. Store the review and all artifacts in the configured app workspace.

Task completion must be observable: preserve the source trigger/guard, handler and service effects; assert the expected success/error/cancel/retry state; compare original/native UI where relevant. A task cannot pass solely because its button, route or manifest ID exists. The shared Wave 0–6 structure is generic; populate its features, symbols, counts, source paths and targets from the current app. Target architecture and task grouping remain human review items.

## Human review and completed source revision

`migration-plan.md` is the short human feature/function checklist only. Curate `humanFeatures` in the manifest from source-backed scope; retain source mappings, waves, dependencies, guards and acceptance criteria in the agent JSON files. Do not present the long technical inventory as the human plan.

After the full migration passes final verification, run `complete-migration --config apps/<app>/migration.json --artifacts <verified-artifacts>`. It records `lastMigratedCommit` and the verified baseline manifest; never advance this value for discovery, partial work or development-only checks. Discovery records `sourceCommit`, and completion requires the same clean source revision.

On later runs, first run `discover-changes --config <config>`. Inspect the diff from `lastMigratedCommit`, including deletions/renames and affected importers, service/library dependencies and UI states. Reuse the completed inventory for unchanged scope. The current static discovery command still performs a full scan; use the change list to direct agent reconciliation rather than claiming an incremental parser is implemented. Missing history, changed dependency/theme/router configuration or broad shared changes can require a wider refresh.
